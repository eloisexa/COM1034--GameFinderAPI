## 3. Data Model

<!-- Description of the data model, including tables/entities and relationships. Include a UML diagram and also update `db/extended_schema.sql`. You can use `db/original_database_schema.md` as a reference for how to structure the SQL schema for your new feature.  -->

The updated extended schema demonstrates the wishlist feature to allow users to save games to their wishlist, and a recommendations table which stores generated recommendations from the 'What Should I Play?' feature. 

Tables: 
* USERS: 
    * Stores basic user information. 
    * userID - Primary key 
    * username 
    * email 

* WISHLISTS: 
    * Each user has one wishlist. 
    * wishlistID - Primary key
    * userID - Foreign key to USERS 
* WISHLISTITEMS: 
    * Links a game to a user's wishlist. 
    * wishlistID - Foreign key to WISHLISTS 
    * gameID - Foreign key to GAMES 
    * dateAdded 
* RECOMMENDATIONS: 
    * Links recommended games to users and contains a unique ID to be called at generation. 
    * recommendationID - Primary key 
    * userID - Foreign key to USERS 
    * gameID - Foreign key to GAMES 

Overall Relationships: 
* USERS - WISHLISTS (1 : 1)
* WISHLISTS - WISHLISTITEMS (1 : Many)
* GAMES - WISHLISTITEMS (1 : Many)
* USERS - RECOMMENDATIONS (1 : Many)
* GAMES - RECOMMENDATIONS (1 : Many)


## 4. Design Decisions

<!-- Key architectural and data model decisions made by the team. -->
The team has made multiple architectural decisions to help maintain and develop our data model. 

* Modular architecture: 
The data model is split into independant modules (Wishlist, Recommendations and Users). This approach allows us to develop, test and maintain each component independantly; moreover, it also allows easier implementation of new features without affecting the entire system as a whole. 

* Normalised relational database: 
We chose a normalised relational database model to ensure that data is consistent through foreign key constraints. This structured storage of information also ensures efficient querying and avoids unecessary complexity in managing multiple lists per user.  

* Recommendation approach: 
The generated recommendations are stored in a database which reduces repeated computation, improving overall performance and decreasing resource usage. 

* Privacy: 
Only the user's essential data is stored in the database (username and email) which minimises any risk of this database being accessed by foreign sources. Behavioural data such as mood and playtime (used to generate recommendations) should be optionally stored and anonymised where possible. 


## 5. Legal, Sustainability and Ethical Considerations

<!-- Consider the legal, sustainability, and ethical implications of your design. Discuss how your design addresses these considerations and any trade-offs that were made. -->

Legal:
* Data protection:
    * Storing user accounts therefore user’s personal data will be stored and needs to be protected under the Data Protection Act
    * Mood and habitual data are extra sensitive and must be handled accordingly
    * Data collection must be defined, and reasons for why and how long kept for should be defined when consent is requested
    * Data must be exportable and deletable
* AI considerations:
    * Rights for the use of the simplified AI required
    * Could include a ‘why is this recommended’ button to explain to the user the reasoning and responsibilities/requirements followed behind the use of AI 
* Age considerations:
    * Parental consent for minors required as well as extra data protection and protective measures put in place to ensure safety and privacy of data
    * Could add a personalisation/account free mode - requires no personal data to be entered
* Intellectual property and copyright:
    * Need to create a legal distinction between similar services, such as Steam of Epic Games with design and features
    * Game metadata must be acquired with the proper permissions
    * Could be issues with producer’s terms of service for AI (or other services/content) intended on using
* Regional laws:
    * Enforce digital IDs being required to access games intended for adults (18+)
    * Wishlist could have legal repercussions:
    * Depends on how data is used - user’s personal data could be sold to advertisers/companies so that they can target their games + products towards other users, or users on other applications entirely
    * Can be solved by adhering to strict company policy towards use and sharing of personal, private data, and by implementing hierarchical access to user data

Ethical:
* Algorithmic fairness:
    * The ‘What should I play tonight’ feature shouldn’t be biased towards popular games and should randomise games from the pool that closely match how many hours and genres the user would like
    * Considers bias by prioritising sustainability over popularity so that specific genres and games arent prioritised over others - aims to push less popular games to ensure growth of different game creators/developers
* User wellbeing:
    * As the feature tracks time spent playing games, if the user has played for an extended amount of time without any breaks the app could notify and remind the user to take breaks for their own wellbeing
* Data transparency:
    * Users should clearly understand what data is being collected from them, like the mood inputs, game preference and playtime and how it influences their recommendations
    * This should be communicated in plain language and should not be hidden under terms and conditions
* Accessibility:
    * The app should be accessible to people with visual impairments or disabilities, with accessibility guidelines like colour contrasts and screen reader compatibility

Sustainability:
* We will be using an AI model to generate which game(s) should be played next (for recommended feature), which consumes a lot of resources - especially if there are multiple users using the feature/software at the same time
    * To combat this, we would use a simpler version of AI software (compared to current prominent models such as ChatGPT or Claude) as it will be less resource intensive
